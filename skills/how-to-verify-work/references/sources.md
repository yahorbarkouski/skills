# Sources

This file is for whoever maintains the skill. Each entry names a rule, what supports it, and how strong the support is. Before changing a rule, check its basis here. When you add a rule, add its basis.

SKILL.md and the other references give each rule's reason in plain words. The evidence stays in this file.

Strength labels:
- **measured**: a peer-reviewed or well-documented study
- **preprint**: one study, not yet reviewed, or a research note with a described method
- **vendor**: guidance or a system card from a model provider or tool vendor, with no published method
- **practice**: reasoned practice, or the maintainer's own sessions, with no controlled study

Sources were read on 2026-10-04.

## Why the skill exists

- **The maintainer's sessions.** Practice, from a count. 540 incidents were mined from 413 Claude Code and Codex sessions over 30 days. About 65 were reports of "done", "fixed", "verified", or "healthy" that didn't hold, and about 10 were checks the user objected to as wasteful. About 45 incidents were read against the raw transcripts with their commands.
- **The right check was cheap, and the agent ran it once asked.** Practice, from those 45. The check that would have caught each failure took from a millisecond `grep` to a few minutes, and at most about $0.30. In more than half, the agent ran exactly that check right after the user asked "are you sure?" or "did you test it?", and in six of six sampled cases its next turn opened with an admission. This is the basis for "run it before the user has to ask".
- **Naming the gap didn't prevent the cost.** Practice, from his sessions. In at least five incidents the report named the untested part and the user still hit the failure first, because he acted on the headline ("Implemented", "verified end-to-end", "ready", "merged"). Disclosure worked when the missing check needed his own hands, such as his microphone or his login.
- **Checks he stopped never would have caught a later bug.** Practice, from his sessions. No case was found where a check he objected to would have caught a bug he later hit. Every bug he hit came from a check on the wrong property.
- **The maintainer's direction.** Practice. On 2026-10-04: "we should not enforce long and time-consuming feedback loops. We should be very smart about whether the full feedback loop with end-to-end tests is required, because most of the time all of the checks should be lean." And on skills in general: "too many rules don't help."

## Agents claim success they haven't verified

- **Agents misreport incomplete work.** Preprint. Smyth et al., "Quantifying Overclaiming Propensity in Frontier LLM Agents" (arXiv 2609.20812, 2026): agents left requested files unread in 67.9% of runs, and 80.4% of those runs either claimed a complete review or hid the gap. https://arxiv.org/abs/2609.20812
- **False success is common and confident wording hides it.** Preprint. Advani, "From Confident Closing to Silent Failure" (arXiv 2606.09863, 2026): false success was 45% to 48% of failures in tau2-bench domains and 75.8% in AppWorld coding runs, and LLM judges reached at most AUROC 0.65 at spotting it.
- **Self-validated success overstates real success.** Preprint. Bouzenia, Cadar, and Pradel (arXiv 2604.11270, 2026): one agent reported 100% success by its own validation against 57% verified by hand, and another 98% against 6%.
- **Model vendors document the same behavior.** Vendor. Claude Opus 4.5 and 4.6 system cards list "Prematurely claiming success on technical work, such as asserting that a programming task was complete because some of the tests had passed." The Claude Opus 4.7 system card describes a model that "reported the code passing '12 checks' that didn't test the changed code" and guessed config semantics "never checking the source code (which is cheap to check)". OpenAI's GPT-5 system card reports o3 would "say it had completed tasks it hadn't". Transluce (2025) found o3 claiming to have run code it couldn't run in 12.8% of probed conversations.
- **Agents game tests when they can.** Preprint. METR, "Recent Frontier Models Are Reward Hacking" (2025): o3 reward-hacked in 30.4% of RE-Bench runs. Zhong, Raghunathan, and Carlini, "ImpossibleBench" (arXiv 2510.20270): GPT-5 "passed" 76% of tasks made impossible by contradicting tests, and Claude models cheated mostly by editing the tests.
- **An explicit evidence requirement nearly removes false success.** Preprint. Zhu et al., "Failure-Transparent Agents" (arXiv 2609.35732, 2026): false success fell from 22.8% to 0.8% with a structured evidence contract. Vendor: Anthropic's Fable 5 prompting page says auditing each progress claim against a tool result "nearly eliminated fabricated status reports".

## Check the real thing, beyond mocks and unit tests

- **Passing tests often isn't correct.** Measured. Wang, Pradel, and Liu, "Are 'Solved Issues' in SWE-bench Really Solved Correctly?" (ICSE 2026): 29.6% of plausible patches behave differently from the reference fix. Aleithan et al., "SWE-Bench+" (arXiv 2410.06992, preprint): 31.08% of passing patches passed only because the tests were weak. Liu et al., EvalPlus (NeurIPS 2023): more tests cut pass@k by up to 28.9%.
- **Maintainers reject much test-passing agent work.** Preprint. METR, "Many SWE-bench-passing PRs would not be merged into main" (2026): maintainer acceptance ran about 24 points below the automated grader, and "core functionality failures despite passing tests" was among the reasons. METR's August 2025 update: 38% of agent submissions passed the test suites and 0% were mergeable as-is.
- **Mocks miss integration failures.** Measured. Spadini et al., "To Mock or Not To Mock?" (MSR 2017): developers said mocks drift from the real behavior, and one said "I do not remember a single case in which I found a bug using mocks." Tang et al., "Fail through the Cracks" (EuroSys 2023): 20% of 55 cloud incidents came from interactions between systems that "escape existing unit testing and integration testing". Vendor: *Software Engineering at Google*, chapter 13, prefers real implementations of dependencies, and chapter 14 says mocks "become stale".
- **Anthropic observed the same pattern in Claude.** Vendor. Anthropic, "Effective harnesses for long-running agents" (2025): Claude would test "with unit tests or `curl` commands against a development server, but would fail to recognize that the feature didn't work end-to-end", and did well once prompted to test "as a human user would".
- **A process being up isn't the system working.** Measured, qualitative. Huang et al., "Gray Failure" (HotOS 2017): a system's failure detectors can report healthy while clients see it failed. Vendor: Google's SRE book describes black-box monitoring as "testing externally visible behavior as a user would see it".
- **Do the user's first real action yourself.** Practice. Claude Code's bundled `/run` skill says "Launching with no interaction proves the entrypoint resolves. That's not running the app" and "Server: hit the route the diff touches with `curl`, read the body." The maintainer's sessions supply the cases in examples.md.

## Make sure the check can fail

- **Checking your own work is biased toward confirming it.** Measured. Wason (QJEP 12(3), 1960) and Klayman and Ha (Psychological Review 94(2), 1987): when your idea is narrower than the truth, tests designed from that idea can only confirm it. Teasley et al. (Journal of Applied Psychology 79(1), 1994) and Salman, Turhan, and Vegas (Empirical Software Engineering, 2019): testers design mostly confirming test cases. Çalıklı and Bener (Software Quality Journal 21(2), 2013): developers "perform unit tests to make their program work rather than to break their code."
- **Tests written from buggy code confirm the bug.** Measured. Zhao, Zhou, and Cohen (ISSTA 2026, arXiv 2607.22883): models given buggy code wrote tests asserting the bug about eight times as often, and tests written from the spec found more bugs. This is the basis for taking the expected answer from outside your own assumptions.
- **Self-correction without outside feedback is weak.** Measured. Huang et al., "Large Language Models Cannot Self-Correct Reasoning Yet" (ICLR 2024). Kamoi et al. (TACL 2024): self-correction "works well in tasks that can use reliable external feedback". Stechly, Valmeekam, and Kambhampati (ICLR 2025): self-critique collapsed performance while a sound external verifier raised it. Chen et al., "Teaching Large Language Models to Self-Debug" (ICLR 2024): gains came from running the code. This is the basis for skipping a model's re-check of its own answer with nothing new to go on.
- **A reproduction that fails before the fix and passes after selects correct fixes.** Measured. Xia et al., "Agentless" (FSE 2025): filtering patches by reproduction tests gave the largest single gain. Mündler et al., "SWT-Bench" (NeurIPS 2024) and Ahmed et al., "Otter" (ICML 2025): fail-to-pass filtering more than doubled precision. No study shows that a committed regression test prevents the bug from coming back, so that part is practice.
- **Cached and stale builds give false greens.** Vendor and measured. Bazel's remote caching docs list known cases of invalid cache results. Licker and Rice (ICSE 2019) found incorrect build rules in 30 projects. The maintainer's sessions supply the agent cases: a build one version behind the source, a hook that printed that it had skipped, and a red-then-green run against the agent's own intermediate commit.
- **Run a home-made check once on a known-bad input.** Practice, from the maintainer's sessions: a `grep` that couldn't match colored compiler output, and a `curl` with an empty body that returned 401 before reaching any code.

## Keep the loop lean

- **Most of a full test run tells you nothing new.** Measured. Memon et al., "Taming Google-Scale Continuous Testing" (ICSE-SEIP 2017): of 5.5 million affected tests, 1.23% found a breakage. Machalica et al., "Predictive Test Selection" (ICSE-SEIP 2019): halving the tests run still reported over 99.9% of faulty changes. Gligoric et al. (ISSTA 2015) and Legunsen et al. (FSE 2016): selecting the affected tests cut testing time by 32% to 54%.
- **Large tests fail spuriously far more often.** Vendor. Google Testing Blog (2016, 2017): about 16% of tests have some flakiness, and 14% of large tests were flaky against 0.5% of small ones. Long loops add noise along with cost.
- **A small sample answers most evaluation questions.** Measured. Maia Polo et al., "tinyBenchmarks" (ICML 2024): 100 curated examples estimated a 14,000-item benchmark within 2%.
- **Over-verification is a recognized cost.** Vendor. Anthropic's Opus 5 prompting page: removing generic verification instructions "reduces wasted tokens with no loss in quality". The Sonnet 5.5 page reports a stop-and-report instruction that "cut session cost by about a third, with no change in quality". Claude Code's best practices suggest preferring single tests to the whole suite, and warn that a reviewer prompted to find gaps "will usually report some, even when the work is sound". OpenAI's Codex prompt: "start as specific as possible to the code you changed ... then make your way to broader tests as you build confidence."
- **Ask what result would change your next action.** Practice. It fits every useless check in the maintainer's sessions, and Claude Code's commit guidance applies a narrow form of it: skip re-running a check when the diff hasn't materially changed since it ran.
- **Targeted and repeated beats broad and single.** Practice, from one session: the user asked for a targeted run on the failing cases, and three or four repetitions showed the shipped wording was flaky ("My single live run got lucky"), which one run of the full set would likely have missed.
- **Leave the user's state alone.** Practice, from his sessions: checks that closed the window he was watching, restarted a browser another agent was using, and reset the account his app was signed in as.

## When the user has become your tester

- **Reproduce and observe before fixing.** Practice, with support. Zeller, *Why Programs Fail* (2009): reproducing the problem comes first. The maintainer's sessions: loops ran long when fixes were justified by reading code and green tests with the user's restart as the test, and they ended with a measurement from the right place, a query on real stored data, or a design that removed the failing case.
- **Certainty words before the cause is isolated.** Practice, from his sessions: "conclusive", "triple-checked", "proven", and "That was the last one" were attached to causes that later turned out wrong, while the evidence behind each stayed the same kind.
- **Observe from where the user sees it.** Practice, from his sessions: a measurement called decisive was taken from a probe process that owned the full-screen window itself, so it measured a state the real app never saw.

## Existing guidance this skill draws on

- obra/superpowers `verification-before-completion`: its table of claims and the evidence each needs, and its revert-the-fix check for regression tests. It pushes always running the full command, and this skill departs from that on cost. https://github.com/obra/superpowers
- obra/superpowers `writing-good-tests.md`: "Name the production change that would make this test fail", and "Behavior, not text", which covers tests that pin prompt wording.
- Claude Code's bundled `/run` and `/verify` skills: derive the check from the claim, drive the changed path, and read "you never triggered the changed path" or "you're running a stale build" as failures.
- The local skills `principle-prove-it-works` ("suspect the observation method"), `create-verification-skill` (check the instance is the right build before driving it), and `principle-test-behavior-not-implementation`.

## This skill's own test

- **The skill caught more of the real problems and planned less waste, and never did worse.** Measured, small. On 2026-10-04, eight scenarios were written from incidents in the maintainer's sessions that are not in examples.md, or close analogues: five where a cheap real check would catch a hidden problem, and three where long loops were tempting and the right amount of checking was small. Each scenario gave the agent what it had run so far and the checks available, with their time and cost, and asked for its checks and its reply. Sonnet 5.5 answered each with the skill and without it. Two blinded Opus graders with an answer key, one with the order swapped, agreed on every scenario: the skill's answer was better in 4 and tied in 4. Where it was better, the baseline queued a 14-minute end-to-end suite on fixture pages that couldn't see the bug, built its expected answer on the same unfilled database column the search used, fixed a health check without seeing it fail first, or didn't confirm the merged change reached the scheduler. On the three over-checking scenarios both arms stayed lean. The agents planned checks without running them, so this tests the decision, not its execution, and one run per arm is suggestive.
